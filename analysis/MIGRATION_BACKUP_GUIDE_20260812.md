# stock-alert-app 他サーバー移行時のバックアップ・復元手順

## 目的

この手順は、現在のアプリを別サーバーへ移す際に、取引履歴、1分足データ、シグナル検証データ、コード、ローカルのKABUステーション連携設定を失わないためのものです。

> **重要:** 移行作業中は `DRY_RUN=True` を維持し、実発注を開始しないでください。移行完了後に、まずデータ受信とシミュレーションを確認してから自動売買のテストを再開します。

## 1. 退避対象

| 区分 | 退避対象 | 優先度 | 理由 |
|---|---|---:|---|
| ソースコード | プロジェクト一式、Git履歴、`package.json`、`pnpm-lock.yaml`、`drizzle/`、`server/`、`client/`、`shared/`、`analysis/` | 必須 | アプリ本体、シグナル仕様、DBスキーマ、分析資産を復元するため |
| 本番DB | 下記の全テーブル | 必須 | 取引履歴・1分足・日次集計・自動売買指示を復元するため |
| 環境変数 | **値は平文で保存せず**、変数名・用途の一覧だけを保存。新サーバーで再設定 | 必須 | DB接続・認証・アプリ設定を再構成するため |
| ローカルrelay | `kabu_board_relay_v6_0.py`、WindowsタスクスケジューラーのXML、起動用bat/ps1があればそれも | 必須 | KABUステーションから新サーバーへ1分足を送信するため |
| 運用資料 | 現行エンジン仕様書、v6.0自動売買仕様書、日次ログ | 推奨 | 移行後の動作照合・障害調査に使うため |
| S3等のファイル | アプリが保存している添付・画像等があればその一覧と実ファイル | 必要時 | 現行構成では中心データはDBだが、使用している場合は別途コピーが必要 |

## 2. 本番DBで退避するテーブル

現在確認できるテーブルは以下です。全テーブルを一括で退避します。

| テーブル | 主な内容 |
|---|---|
| `rt_candles` | KABUステーション受信の1分足・板情報。検証に最重要 |
| `rt_trades` | リアルタイムシミュレーションのエントリー・決済・損益 |
| `rt_daily_summaries` | 日次の損益・取引件数などの集計 |
| `rt_3peak_signals` | 3山シグナルの記録 |
| `rt_score0_blocks` | 板読みスコア0でブロックされたケース |
| `auto_trade_daily` | 自動売買の日次状態・集計 |
| `order_instructions` | ローカルexecutor向けの注文指示・実行状況 |
| `__drizzle_migrations` | DBスキーマの適用履歴 |

## 3. バックアップ実施順序

### A. まずコードを固定する

1. GitHub連携済みなら、最新チェックポイントを保存してGitHub側へ同期します。
2. GitHubを使わない場合は、プロジェクトフォルダをZIP化します。ただし `node_modules` と秘密情報ファイルは含めません。
3. `analysis/ENGINE_SPEC_20260809.md`、`analysis/AUTO_TRADE_IMPL_SPEC_v6.md`、`analysis/MIGRATION_BACKUP_GUIDE_20260812.md`を含めます。

### B. DBを停止中に一貫した状態で退避する

移行中にデータが追加されないよう、Windows側relayを一時停止します。自動売買は必ず `DRY_RUN=True` のままにします。

MySQL/TiDB互換DBを使用する新サーバーへ移す場合の例です。接続情報をコマンド履歴に残さないため、接続文字列は環境変数から渡します。

```bash
# 移行元で実行する例
# DATABASE_URLは画面やシークレット管理から安全に設定する。値をチャット・Gitに書かない。
mysqldump --single-transaction --routines --triggers \
  --databases "${DB_NAME}" > stock_alert_backup_YYYYMMDD.sql

# バックアップが壊れていないことを確認
ls -lh stock_alert_backup_YYYYMMDD.sql
head -20 stock_alert_backup_YYYYMMDD.sql
```

`mysqldump`を使えない管理型DBの場合は、DB管理画面または提供元のスナップショット／エクスポート機能で**全テーブルとスキーマを含むSQL形式**で出力します。CSVをテーブルごとに出す方法は復元順・型・インデックスを別管理する必要があり、第一選択にはしません。

### C. Windows側のrelayを退避する

Windows PCで以下を一つのフォルダにまとめ、暗号化ZIP等で保管します。

```text
relay-backup/
├─ kabu_board_relay_v6_0.py
├─ task-scheduler-export.xml
├─ 起動用のbatまたはps1（存在する場合）
├─ requirements.txt または Pythonライブラリ一覧
└─ 直近数営業日のrelayログ
```

タスクスケジューラーは対象タスクを右クリックして**［エクスポート］**を選び、XMLで保存します。特に、Python実行ファイル、relayスクリプトの絶対パス、開始フォルダ、実行アカウント、トリガーを移行先で再現できるようにします。

> APIトークンは毎日失効するため、バックアップ対象ではありません。KABUステーションのログイン情報やAPIパスワードをソースコード、ZIP、Git、チャットに保存しないでください。

## 4. 新サーバーへの復元順序

1. 新サーバーにNode.js 22系、pnpm、MySQL/TiDB互換DBを準備します。
2. GitHubからコードを取得し、`pnpm install --frozen-lockfile`を実行します。
3. 新DBを作成し、SQLバックアップをインポートします。

```bash
mysql -h <new-db-host> -u <db-user> -p <new-db-name> < stock_alert_backup_YYYYMMDD.sql
```

4. 新サーバー側のシークレット管理に、DB接続、セッション署名鍵、OAuth設定、アプリURLなどを**新規に設定**します。旧サーバーの秘密値をGitへコピーしません。
5. `pnpm check`、テスト、DBの行数照合を行います。
6. 新サーバーのURLでアプリを起動します。この時点ではrelayの送信先を変更せず、アプリ単体の画面・DBが正常に読めることを確認します。
7. Windows relayの`CLOUD_BASE_URL`を新しいHTTPS URLへ変更し、タスクスケジューラーで実行ファイルパスが正しいことを確認します。
8. `DRY_RUN=True`で1分足が新DBへ届くこと、全20銘柄が受信されること、シミュレーションが動くことを確認します。
9. 旧サーバーと新サーバーの最新`rt_candles`時刻、銘柄数、`rt_trades`件数を比較します。両方が一致することを確認してから、旧サーバーのrelay送信を停止します。
10. 自動売買は、移行後のDRY_RUN確認を終えるまで`DRY_RUN=False`に切り替えません。

## 5. 移行完了判定チェックリスト

| 確認項目 | 合格条件 |
|---|---|
| コード | 新サーバーで依存関係のインストール、型チェック、テストが通る |
| DB | 全8テーブルが存在し、テーブルごとの行数が移行元と一致する |
| 1分足 | 新DBの`rt_candles`に当日分が入り、20銘柄を受信する |
| シミュレーション | `rt_trades`と`rt_daily_summaries`が新サーバーに作成される |
| relay | ログに新URLへの送信成功が出る。送信失敗・401・接続例外が継続しない |
| 自動売買 | まず`DRY_RUN=True`で状態遷移を確認する。実発注はその後に段階的に再開する |
| 切戻し | 旧サーバーのコード、DBバックアップ、relay設定XMLが手元に残っている |

## 6. このアプリ固有の重要注意点

KABUステーションAPIはWindows PCのローカルアドレスで稼働するため、アプリを外部サーバーへ移しても、**relayはWindows PCに残す必要があります。** 新サーバーはシグナル判定・DB・画面を担い、Windows relayはKABUステーションから1分足を取得し、新サーバーへ送信します。

そのため移行の本質は「Windowsから送信する先URLを、安全に新サーバーへ切り替えること」です。relayで実発注を使う場合も、発注先は引き続きWindows PC上のKABUステーションAPIです。

## 7. 実施時の推奨方針

最も安全なのは、営業日の日中ではなく、取引終了後または休日に作業することです。切替後の最初の営業日は`DRY_RUN=True`で受信確認だけを行い、実発注設定を維持したまま切り替えないでください。
